J-Link RTT 연결 메커니즘

타겟 RAM의 _SEGGER_RTT Control Block을 호스트 J-Link가 SWD로 폴링·읽기/쓰기하는 구조, 보드 전원 OFF 시점의 신호 동작, pylink-square API의 알려진 함정, 그리고 본 도구의 이중화 끊김 감지가 도출된 근거를 정리합니다.

1. J-Link RTT 개요

flowchart LR
    PC["PC
auto-rtt-viewer"]
    JL["J-Link Probe"]
    MCU["MCU
Cortex-M3"]
    RAM[("Target RAM
SEGGER_RTT CB + Up/Down 버퍼")]

    PC <-->|USB, JLinkARM.dll| JL
    JL <-->|SWD| MCU
    MCU <-->|메모리 버스| RAM
    JL -.RAM read/write.-> RAM
  • RTT(Real-Time Transfer): 타겟 RAM에 _SEGGER_RTT Control Block(이하 CB)을 두고, 호스트 J-Link가 SWD로 RAM을 직접 읽고 써서 비침습적(non-intrusive) 통신을 구현.
  • CB 내부에 Up 채널(Target→Host)과 Down 채널(Host→Target) 원형 버퍼 포인터가 들어 있다.
  • 호스트가 주기적으로 RAM을 폴링하며 Up 버퍼에서 읽고, Down 버퍼에 쓰는 구조. 타겟 CPU halt 불필요.
  • CB 검색은 RAM 영역에서 SEGGER RTT\0 매직 문자열을 스캔하거나, 고정 주소 지정 방식.

2. 연결이 끊어지는 실제 시점

이벤트신호 레벨감지 포인트
타겟 보드 전원 OFFSWD가 high-Z / 응답 없음다음 RTT read 시 실패 / target_connected() False
USB 연결 끊김J-Link DLL 핸들 무효opened() / connected() False
타겟 MCU halt/resetSWD는 살아있지만 RTT 버퍼 포인터 리셋 가능내용 이상, CB 재검색 필요
펌웨어가 SWD 핀을 GPIO로 설정디버그 인터페이스 소실명령 실패
Important
실제 현장에서 가장 자주 발생하는 시나리오는 "타겟 전원 OFF → 잠시 후 ON" (보드 리부팅). USB·J-Link 프로브는 계속 PC에 붙어 있다.

3. pylink-square가 제공하는 상태 확인 API

API반환의미
jlink.opened()boolDLL이 열려 있는가 (프로브와 통신 가능한가)
jlink.connected()boolJ-Link 프로브 자체와 host 간 통신 가능
jlink.target_connected()boolSWD 너머 타겟 MCU가 살아 있는가
jlink.rtt_read(ch, n)list[int] (bytes)RTT upchannel 바이트 수령. 실패 시 예외
jlink.rtt_write(ch, b)int (written)RTT downchannel 쓰기

알려진 함정

  • pylink #144: connect()가 예외 없이 끝나도 target_connected()가 False일 수 있음. 명시적 검사 필수.
  • pylink #249 / #178: rtt_start()의 CB 자동 검색이 일부 MCU에서 실패. Fallback으로 명시 주소 / 검색 범위 지정 옵션을 구현에서 준비.
  • target_connected() 단독으로는 타겟 전원 OFF 즉시 감지 보장 안 됨. J-Link DLL이 내부 캐시 상태를 반환할 수 있어 전원이 꺼져도 한동안 True가 유지된다(현장 관측). 또한 rtt_read()도 상황에 따라 예외를 던지지 않고 빈 바이트 리스트만 조용히 반환하는 경우가 있어 reader 태스크가 끊김 감지 신호를 내지 못할 수 있다.
    • 대응: supervise 루프에서 target_connected() 폴링에 더해, 프로파일에 알려진 RTT CB 주소(또는 검색 범위 시작 주소)로 주기적 memory_read32 호출을 병행. 전원 OFF 시 SWD 응답이 없어 예외가 발생하므로 즉시 끊김 판정 가능. CB 주소가 없는 cb_search.mode=auto 프로파일은 이 보강이 적용되지 않으며 target_connected() 한계에 그대로 노출된다.
  • 예외 타입은 대부분 pylink.errors.JLinkException 계열.
  • J-Link DLL은 단일 프로세스 전용. JFlash / Ozone / SEGGER RTT Viewer GUI / auto-rtt-viewer가 모두 JLinkARM.dll을 직접 열기 때문에 동시 열람 불가. 상대 도구가 DLL을 잡고 있으면 Could not open J-Link ... already in use 계열 예외 발생. auto-rtt-viewer는 자동 재시도 루프이므로 상대 도구 해제 시 자연스럽게 복구됨(예: JFlash 다운로드 → 종료 → 즉시 재연결).

4. "초기 부팅 메시지를 놓치지 않는" 조건 분석

수용 기준 AC2를 충족하려면 다음이 필요하다.

sequenceDiagram
    participant Host as auto-rtt-viewer
    participant Probe as J-Link 프로브
    participant MCU as 타겟 MCU
    participant RTT as RTT CB (in RAM)

    Note over MCU: 전원 OFF
    loop 짧은 주기로 재시도
        Host->>Probe: connect(chip)
        Probe-->>Host: 실패 (target 없음)
    end
    Note over MCU: 전원 ON → 부팅
    MCU->>RTT: SEGGER_RTT_Init() (부트로더 초기)
    Host->>Probe: connect(chip) (곧바로 다음 재시도)
    Probe-->>Host: 성공
    Host->>RTT: rtt_start() → CB 검색
    RTT-->>Host: CB 주소 확정
    loop 높은 빈도 폴링
        Host->>RTT: rtt_read(ch 0)
        RTT-->>Host: 부팅 메시지 (누락 없음)
    end

4.1 메시지 유실 가능성

  • 타겟 Up 버퍼는 원형. 호스트가 읽지 않으면 버퍼가 가득 찬 뒤 기본 모드(SEGGER_RTT_MODE_NO_BLOCK_SKIP)에서는 덮어써진다.
  • Sound1의 RTT 버퍼 크기와 부팅 직후 출력량을 정확히 알지 못하므로, 재연결 지연 자체를 최소화하는 것이 가장 안전한 대책.
  • Sound1은 CB 주소가 고정(0x20000000)이므로 rtt_start(block_address=0x20000000) 직행 → 일반적인 CB 자동 검색(수 ms ~ 수십 ms) 단계를 건너뛴다.

4.2 짧은 재시도 주기의 비용

  • J-Link SDK는 내부적으로 SWD에 전기적 신호를 보내므로, 너무 공격적인 주기(수 ms 수준)는 USB 트래픽 · 타겟 영향 · 타 디버거 점유와 충돌 가능.
  • 경험적 권장치는 50 ~ 200 ms. 본 도구는 기본값 100 ms로 운영.

4.3 타겟 측 요인 (도구 범위 밖)

  • 펌웨어의 RTT 초기화 시점 자체가 늦으면 그 이전 printf는 근본적으로 수집 불가 → 펌웨어 책임.
  • Sound1은 부트로더 초기에 ENABLE_SEGGER_RTT=1로 초기화되므로 이 부분은 이미 유리한 조건.

5. Sound1 (E8300) 실측 설정

항목값근거
J-Link Device NameCortex-M3 (generic)Eclipse Debug launch, Sound1 .cproject
인터페이스SWDlaunch + Sys_DIO_CM3JTAGConfig(true, false) in bootloader/main.c
Clock4000 kHz본 도구가 기본값으로 채택 (현행 기본 프로파일). 과거 기록(1000 kHz)에서 갱신.
RTT CB 주소고정 0x20000000현재 빌드 환경 실측값
RTT 초기화 시점부트로더 초기 (CoreDebug->DEMCR |= TRCENA, ENABLE_SEGGER_RTT=1)bootloader/main.c, ci_initialize.h
공식 SEGGER E8300 프로파일없음SEGGER KB에 명시
Important
Sound1은 RTT CB 주소를 0x20000000로 고정해 rtt_start(block_address=0x20000000)를 호출한다. 이로써 (1) rtt_start() auto-detect 실패 리스크(pylink #249) 회피, (2) CB 검색 단계가 없으므로 재연결 직후 RTT 수신까지의 지연이 추가로 단축 → AC2에 유리.
Warning
E8300은 SEGGER 공식 "Supported Devices" 목록에 없음. 다른 타겟에서 재사용할 때는 설정 파일의 cb_search.mode를 auto 또는 range로 전환해야 한다.

6. 입력(Host → Target) 채널 동작

표준 패턴 (pylink examples/pylink-rtt 참조):

payload = list(bytearray(line, "utf-8") + b"\x0A\x00")
jlink.rtt_write(0, payload)
  • 라인 종결자(\n 또는 \r\n)는 타겟 파서가 기대하는 형식에 따라 달라 설정 가능해야 한다.
  • 입력 소스가 둘 이상일 때(Telnet + stdin) 동시성 문제: 본 도구는 단일 큐로 직렬화하는 방안을 채택 — 도착 순서대로 in_queue에 push, Writer가 단일 소비.

7. Telnet 퍼블리시 동작

  • asyncio TCP 서버(start_server)로 구성.
  • 특이사항: 양방향이다. 클라이언트가 보낸 바이트는 타겟 입력으로 들어가야 하므로, 단순 fanout broadcaster 이상으로 입력 라우팅이 필요.
  • 동시 접속 클라이언트 수 제한은 기본 무제한(allow_multi_client: true). 실제 운용에서는 단일 클라이언트 권장 (입력 충돌 회피).
  • IAC 제어 시퀀스 처리: Telnet의 WILL/DO/SB..SE·escaped FF를 in-stream에서 제거 후 in_queue에 전달.

8. 끊김 감지 이중화 근거

요구사항 F2 "이벤트 + 폴링 이중화"의 현실적 구현:

감지 소스원리장점한계
이벤트rtt_read / rtt_write / 기타 API 호출에서 JLinkException 발생실시간 감지호출이 없을 때는 감지 불가 (idle 시 dead)
폴링별도 타이머로 target_connected() + memory_read32(CB) 주기 조회idle 상태에서도 감지주기 간격만큼 지연

→ 둘을 병행하여, API 예외 시 즉시 재연결 루프 진입 + 폴링으로 보조.

9. 결론 및 다음 단계

  • 구현은 Python + pylink-square가 합리적 선택. JLink.exe CLI 래핑은 예외 포착·성능 면에서 불리.
  • 상시 빠른 재연결 루프 + 양방향 RTT 채널 I/O + 다중 싱크/소스 파이프라인 구조가 필요.
  • 구체값 결정(폴링 간격 100 ms, 입력 라인 종결자 \n, telnet 포트 19021 등)은 아키텍처 §12에서 확정.
